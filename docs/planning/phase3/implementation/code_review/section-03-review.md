# Code Review: Section 03 - Vitest Setup

The implementation is a faithful, minimal execution of the plan. That said, there are several points a critical reviewer would raise:

1. **Conflicting `root` properties (vite.config.js, lines 5 and 11)**: The top-level Vite config sets `root: 'Sources'` (from section-01), and the `test` block overrides it with `root: './'`. While this is likely intentional so Vitest can discover `Tests/**/*.test.js` from the project root rather than from `Sources/`, this creates an implicit coupling that is fragile. If someone removes the test-level `root` override not understanding why it exists, all test discovery breaks silently. There is no comment explaining why the override is necessary. The plan itself never explicitly calls out the need for a `test.root` override -- it says 'include: Tests/**/*.test.js' but does not mention that the top-level `root: Sources` would make that path resolve relative to `Sources/` without the override.

2. **vitest.setup.js is an empty placeholder with no defensive polyfills (line 1-10)**: The plan (section 3.3) explicitly states polyfills 'should be included conditionally (only set if not already defined) to be safe during the transition.' The implementation chose to omit all polyfills entirely, reasoning Node 22+ provides them. This is a reasonable judgment call, but it deviates from the plan's recommendation for defensive conditional polyfills. If CI or any contributor runs on an older Node version or a different jsdom version, tests could fail with cryptic errors about missing `TextEncoder`. A one-liner like `if (!globalThis.TextEncoder) { ... }` costs nothing and provides safety.

3. **No `@vitejs/plugin-vue` verification**: The plan (section 3.1) states '@vitejs/plugin-vue should already be installed from section-01.' The diff does not show this package in devDependencies. If it was not installed in section-01 either, later sections (section-06) will fail. This is not a section-03 blocker but the plan called it out as a dependency assumption worth verifying.

4. **No `exclude` pattern for `All.test.js`**: The `include` pattern `Tests/**/*.test.js` will also match `All.test.js` if it exists in the `Tests/` directory (or project root) when `create_tests.sh` has been run. If a developer runs `npm run test:vitest` after running the Jest pipeline, Vitest could pick up the concatenated `All.test.js` and attempt to run it, which would certainly fail catastrophically since it has no imports. The plan does not address this, but a robust implementation should add `exclude: ['**/All.test.js']` to the test config.

5. **`pool: 'threads'` with `singleThread: true` vs `pool: 'forks'`**: The plan specifies threads with singleThread, which the implementation follows. However, for a project with heavy global state mutation, `pool: 'forks'` with `singleFork: true` might be more appropriate since threads share memory in ways that can cause subtle issues with global state. This is a minor design concern, not a bug.

6. **No evidence of verification steps being executed**: The plan's completion criteria require that `npx vitest run Tests/VitestSetup.test.js` passes and `npm run test:only` (Jest) still passes. The diff is purely code changes with no test output or verification log. This is normal for a diff review, but worth noting that the reviewer cannot confirm criteria 1 and 2 from the diff alone.

Overall severity: The `root` override without documentation (issue 1) and the missing `All.test.js` exclusion (issue 4) are the most practically dangerous issues. Issue 4 in particular is a latent landmine that will cause confusion when both test runners coexist.
