# Code Review: Section 01 - Vite Setup

The implementation is a near-verbatim copy of the plan. It achieves its stated goals, but there are several issues worth raising:

1. **Vite 8 + @vitejs/plugin-vue 6 compatibility risk (package.json lines 32, 36)**: Vite 8.0.1 is installed with @vitejs/plugin-vue 6.0.5. As of the knowledge cutoff, Vite 6 was the latest stable release. Vite 8 is either bleeding-edge or a release candidate. This is a production project -- pinning to a potentially unstable major version is risky. The plan did not specify a version, so the implementer just ran `npm install` and got whatever was latest. There should have been an explicit version constraint or at minimum a comment acknowledging the version choice. If Vite 8 has breaking changes from Vite 6 (the version most documentation references), every downstream section could hit unexpected issues.

2. **rollupOptions.input paths are relative but root-relative resolution is implicit (vite.config.js lines 13-20)**: The input paths like `'AetherRaidSimulator.html'` rely on Vite resolving them relative to the `root` setting (`Sources/`). This works, but it is fragile -- if someone changes `root` or runs vite from a different directory, all 8 paths break silently. Using `resolve()`/`path.join()` with `__dirname` would be more robust, e.g., `path.resolve(__dirname, 'Sources', 'AetherRaidSimulator.html')`. The plan explicitly showed bare strings, so this is a plan-level design issue carried into the implementation.

3. **Tests are string-matching, not structural (Tests/ViteSetup.test.js lines 54-93)**: Every test uses `content.includes()` on the raw file text. The test at line 55 checks `content.includes('root:') && content.includes('Sources')` -- this would pass if 'root:' appeared in a comment and 'Sources' appeared in a completely unrelated context. Same for the `outDir`/`../dist` check at line 62. These tests provide false confidence. A more robust approach would be to dynamically import `vite.config.js` and inspect the resolved config object. The plan prescribed these exact tests, so this is inherited weakness.

4. **No `type: 'module'` in package.json**: `vite.config.js` uses ESM syntax (`import { defineConfig }`, `export default`). Node.js requires either `type: 'module'` in package.json or renaming the file to `vite.config.mjs`. The current package.json (line 1-38) has no `type` field. This means `vite.config.js` will fail to load with a syntax error in Node.js unless Vite has its own loader mechanism that bypasses this. Vite does handle this internally when invoked via its CLI, but the test file `Tests/ViteSetup.test.js` also uses ESM (`import { describe, it } from 'node:test'`), which WILL fail when run via `node --test Tests/ViteSetup.test.js` without `type: 'module'`. This is a real bug -- the verification step in the plan (`node --test Tests/ViteSetup.test.js`) will crash.

5. **manualChunks set to undefined is misleading (vite.config.js line 25)**: Setting `manualChunks: undefined` is the same as not setting it at all. The comment says it will be configured in Section 02, but having it explicitly set to `undefined` with a long comment creates the illusion that something meaningful is configured. This is dead code that adds confusion.

6. **Empty resolve.alias object (vite.config.js lines 29-34)**: The entire `resolve.alias` block contains only comments. An empty object with commented-out code is noise. It would be cleaner to add this block in Section 06 when it is actually needed, or at minimum document why it must exist now.

7. **@vitejs/plugin-vue installed prematurely**: The plan justifies this as 'to avoid a separate install step,' but installing a dependency that will not be used until Section 06 adds unnecessary weight to node_modules and creates a version drift risk. By the time Section 06 arrives, the installed version may be outdated or incompatible with whatever Vue 3 version is chosen.

8. **No verification that existing tests still pass**: The plan's verification section says to run `npm run test:only` to confirm no regression, but there is no evidence in the diff that this was done. The package-lock.json shows `@jridgewell/sourcemap-codec` was upgraded from 1.4.15 to 1.5.5 as a transitive dependency change -- this kind of silent upgrade could introduce regressions.

The critical issue is #4 -- the ESM test file will not run without either `type: 'module'` in package.json or renaming to `.mjs`. This means the prescribed verification step is broken.
