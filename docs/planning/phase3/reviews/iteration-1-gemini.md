### 1. アーキテクチャとビルド設定の罠 (Step A & C)

**🚨 [フットガン] 1ファイル出力の強制 (A.2)**
*   **問題:** Rollup/Viteでマルチエントリー（8つのHTML）から「完全に独立した8つの1ファイルJS」を出力しようとすると、Vue本体、Pinia、共通ロジックが8つのファイルすべてに重複してバンドルされ、ビルド時間とファイルサイズが劇的に悪化します。
*   **解決策:** デプロイ担当者と協議し、「`dist/assets/` に共通チャンク（`vendor.js` 等）を出力する」標準的なViteの挙動を許容できないか確認してください。どうしても1HTMLにつき1JSファイルにする必要がある場合は、Viteのマルチページ機能ではなく、Viteのビルドコマンドを8回ループで実行するスクリプトを書く方が確実で安全です。

**🔍 [考慮漏れ] Viteの `root` 設定とアセット解決 (A.2 & C.3)**
*   **問題:** HTMLファイルが `Sources/` 配下にある場合、`vite.config.js` で `root: 'Sources'` を指定しないと、開発サーバーのURLが `http://localhost:5173/Sources/index.html` になり、HTML内の相対パス（CSSや画像など）の解決が壊れる可能性が高いです。
*   **解決策:** `vite.config.js` に `root: 'Sources'` と `build.outDir: '../dist'` を設定し、プロジェクトルートとソースルートのズレを吸収してください。

### 2. Vue 3 移行における致命的な見落とし (Step D)

**🚨 [フットガン] HTML内テンプレートのコンパイル (D.1 & A.1)**
*   **問題:** 現在、SFC（`.vue`）を使わず、HTMLファイル内に直接Vueのテンプレートを記述しています。Vue 3のデフォルトのnpmパッケージは「ランタイム専用（コンパイラなし）」です。このままビルドすると、ブラウザ上でHTML内の `{{ }}` や `v-if` が評価されず真っ白な画面になります。計画にある `@vitejs/plugin-vue` はSFC用なので今回は役に立ちません。
*   **解決策:** `vite.config.js` で、Vueのエイリアスをコンパイラ込みのビルド（esm-bundler）に向ける必要があります。
    ```javascript
    resolve: { alias: { 'vue': 'vue/dist/vue.esm-bundler.js' } }
    ```

**🚨 [フットガン] グローバル変数のテンプレート参照 (A.5 & D)**
*   **問題:** 計画には「HTMLテンプレート内の `{{ }}` から参照されるデータ...は残る」とありますが、**Vue 3ではコンポーネントの `data`、`setup`、`methods` 等で明示的に定義されていないグローバル変数（`window.g_appData`など）は、テンプレートから直接参照できなくなりました。**
*   **解決策:** Vue 3の `app.config.globalProperties` にグローバル変数を手動で登録するか、すべてのコンポーネントの `data` または `computed` でグローバル変数をリターンするよう修正が必要です。

**🔍 [考慮漏れ] Vue 2のリアクティビティ起因の破壊的変更 (D.6)**
*   **問題:** Vue 3は `Proxy` ベースになったため、Vue 2で必須だった `Vue.set()` や `this.$set()`, `this.$delete()` が廃止されました。レガシーコードにはこれらが残っている可能性が高いです。
*   **解決策:** Step Dの初期段階で `\$set` や `Vue\.set` をgrepし、通常の代入（`obj.key = value`）に書き換えるタスクを追加してください。

### 3. テスト基盤移行のリスク (Step B)

**🚨 [フットガン] Vitestの並列実行によるグローバル状態の汚染 (B)**
*   **問題:** 元々単一の結合スクリプトで動いていたテストをVitestに移行すると、Vitestはデフォルトで**テストファイルをWorkerスレッドで並列実行**します。もしテスト間で共有されるグローバルなモジュール状態（キャッシュ、シングルトンなど）がある場合、テストがランダムに失敗するFlaky（不安定）なテストの温床になります。
*   **解決策:** 移行初期は `vitest.config.js` で `poolOptions: { threads: { singleThread: true } }` （または `--no-threads`）を設定し、直列実行を強制してください。すべての依存関係が完全に分離できた段階で並列化を試みるべきです。

### 4. 移行順序（アーキテクチャ上の問題）(Step D & E)

**⚠️ [アーキテクチャ] Step DとEの順序入れ替え、または統合の推奨**
*   **問題:** 現在の計画では「Vue 3化 (Step D)」を先に行い、その後「jQuery/Select2脱却 (Step E)」を行います。しかし、Vue 3の `Proxy` リアクティビティシステムは、jQueryのようなDOMを直接書き換えるライブラリ（Select2）と非常に相性が悪いです。Step Dの段階で、レガシーなSelect2を無理やりVue 3で動かすための「捨てコード（ラッパーの修正）」を書く羽目になります。
*   **解決策:** 可能であれば、**Step D (Vue 3化) の前に、あるいは同時に Select2 と Vue.Draggable をモダンなライブラリに置き換える**ことを強く推奨します。Vue 2のまま `vue-select` や最新ではないがnpm管理のコンポーネントに移行し、DOMの直接操作を排除してからVue 3へ上げる方が、原因切り分けが容易です。

### 5. その他の追加提案・セキュリティ

*   **Piniaの設計 (D.3):** Vuexの `mapState` から Piniaへの移行時、Vuexは `this.$store` を通じてどこからでもアクセスできましたが、Piniaでは使用する各ファイルで `import { useMainStore } from '@/stores'` を行い、ストアをインスタンス化する必要があります。単なる書き換え以上のimport作業が発生することを計画に織り込んでください。
*   **セキュリティ (E.4):** CDNからnpmへの移行により、`package-lock.json` が生成され、依存関係のツリーが深くなります。Step FのCIパイプライン更新にて、`npm audit` の実行、または Dependabot / Renovate 等の依存関係自動更新ツールの導入を検討事項に追加してください。
*   **`Local.js` の扱い (C.2):** `import.meta.env.MODE` による環境判定は優れています。ただし、開発用のモックデータ（ローカルのweaponInfosなど）が本番ビルドのバンドルに混入しないよう、Viteの動的インポート（`import()`）を活用するか、ツリーシェイキングが確実に効く設計にする必要があります。
