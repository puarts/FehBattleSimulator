# FEH Battle Simulator — コードベース構造改善計画

## 1. 背景と目的

### 1.1 現状

FEH Battle Simulatorは64個のJavaScriptファイル（約15万行、857クラス）で構成されるバニラJSアプリケーションである。すべてのコードがグローバルスコープで動作し、ES modulesは一切使用されていない。HTMLファイルから`loadScripts()`関数で逐次的にスクリプトをロードし、依存関係はロード順序に暗黙的に依存している。

テストは`create_tests.sh`で全ソースファイルを結合し、単一の`All.test.js`をJest + jsdomで実行する方式。本番デプロイは`Deploy.bat`でページごとに異なるファイルセットを結合・JSMin圧縮し、別リポジトリのHTMLから読み込む構成。

### 1.2 本計画の目的

**将来のVite/ESM移行の前段として、コードベースの構造を徹底的に整理する。**

1. **依存関係の可視化**: 暗黙的なグローバル依存を明示化し、全体像を把握する
2. **モジュール境界の確立**: 機能ドメインごとのディレクトリ構成で責務を明確化する
3. **巨大ファイルの解消**: God Object（BattleSimulatorBase等）を責務ごとに分割する
4. **Strict Mode準拠**: 将来のESM化に備えてStrict Mode互換性を確保する

これらが完了した状態で、改めてVite/ESM移行の具体的な計画（「足場」の設計を含む）を策定する。

### 1.3 スコープ

**含まれるもの:**
- Phase 1: 依存関係の可視化と分析
- Phase 2a: ディレクトリ再構成（ファイル移動）
- Phase 2b: 巨大ファイルの責務分割

**含まれないもの（本計画完了後に別途計画）:**
- Vite/ESMへの移行（export/import追加、Vite導入、Vitest移行）
- Vue 2 → Vue 3 アップグレード
- jQuery/jQuery UI除去

### 1.4 制約

- **動作維持**: 各ステップ完了時点でアプリが正常動作すること（テスト + ブラウザ確認）
- **Deploy.bat維持**: デプロイの仕組み（結合+圧縮方式）は変更しない。ただしPhase 2a（ファイル移動）ではパス更新、Phase 2b（ファイル分割）では入力ファイル一覧の変更（旧ファイルの置換または新規分割ファイルの追加）が発生する
- **create_tests.sh維持**: テスト基盤の仕組み（ファイル結合+Jest実行方式）は変更しない。ただしSOURCE_FILE_NAMESの構成はファイル移動・分割に伴い更新する
- **並行開発**: `update_skills`ブランチでスキル実装が継続される。移行はそこから切った別ブランチで行う
- **後方互換性**: セーブデータ（ローカルストレージ）、URLパラメータ、クラス名/プロパティ名を維持
- **期限なし**: 品質優先で段階的に進める

### 1.5 フェーズ概要

```
Phase 1:  依存関係の可視化 + Strict Mode準拠化
Phase 2a: ディレクトリ再構成（物理移動のみ）
Phase 2b: 巨大ファイルの責務分割
――― ここまでが本計画のスコープ ―――
将来:     Vite/ESM移行（別途計画策定）
```

### 1.6 ブランチ戦略

- `update_skills`ブランチから新しい移行用ブランチ（例: `refactor/module-structure`）を作成
- スキル実装の追加は`update_skills`ブランチで並行継続
- 各フェーズ完了時にマージまたはリベース

## 2. Phase 1: 依存関係の可視化

### 2.1 目的

現状の暗黙的な依存関係を明示化し、Phase 2のモジュール設計の基盤とする。また、将来のESM化に備えてStrict Mode準拠を確保する。

### 2.2 グローバルシンボルの抽出

各JSファイルについて以下を抽出する:

- **定義しているシンボル**: クラス定義、関数定義、`const`/`let`/`var`宣言（トップレベル）
- **参照しているシンボル**: 他ファイルで定義されたクラス名、関数名、グローバル変数（`g_`プレフィクス等）
- **副作用の分類**: ファイルロード時に実行されるコードを以下のカテゴリに分類
  - `pure-definition`: クラス/関数/定数の定義のみ
  - `global-assignment`: グローバル変数への代入（例: `g_appData = new AppData()`）
  - `registry-provider`: グローバルレジストリへの登録（例: `Vue.component()`、`SkillEffectRegistrar`への登録）
  - `prototype-extension`: Object.assignによるprototype拡張（Mixinパターン）
  - `initialization-root`: 他の副作用に依存する初期化処理

#### 抽出手法

`madge`等の既存ツールはESM/CJS前提のためグローバルJSには使用不可。以下を組み合わせる:

1. **カスタムAST解析スクリプト**: Acorn/Babel parserで各ファイルのトップレベル宣言と未定義参照を抽出
2. **ESLint `no-undef` ルール**: 暗黙的グローバル参照の検出。各ファイルが「暗黙的に期待している外部シンボル」のリストアップ
3. **実行時グローバル差分**: ブラウザで各ファイルロード前後の`Object.getOwnPropertyNames(window)`差分を記録し、静的解析の結果を補完

### 2.3 依存グラフの構築

抽出結果から以下を生成する:

1. **ファイル間依存グラフ**: ファイルAがファイルBの定義を参照 → A depends on B
2. **循環依存の一覧**: 現在のコードベースで検出される循環参照チェーン
3. **依存レイヤー図**: 依存されるだけのファイル（レイヤー0）から、依存するだけのファイル（最上位レイヤー）まで
4. **各ファイルの副作用分類表**: ESM化時の移行順序判断に使用

### 2.4 Strict Mode準拠化

将来のESM化ではStrict Modeが自動適用される。15万行のバニラJSに非Strict記述（暗黙のグローバル変数宣言、`arguments.callee`等）が含まれている可能性があるため、この段階で準拠を確認・修正する。

**注意**: `create_tests.sh`でファイルを結合するため、個別ファイル先頭への`"use strict";`追加は結合後のファイルでは効かない箇所がある。したがって:

- ESLintの`strict`ルールと関連ルール（`no-implicit-globals`、`no-octal`等）を使って静的にStrict Mode違反を検出
- 発見された問題を修正
- テスト + ブラウザ確認
- `"use strict";`の実際の追加はESM化フェーズまで保留

### 2.5 既知の循環依存とその対処方針

リサーチで以下が特定されている:

| 循環パターン | 現在の緩和 | 将来のESM化時の対処候補 |
|-------------|-----------|----------------------|
| AppData ↔ BattleSimulatorBase | g_appDataシングルトン | 明示的初期化パターン（init/get） |
| Unit ↔ BattleContext ↔ BattleMap | 参照渡し | 型/インターフェース分離または引数注入 |
| DamageCalculator ↔ PostCombatSkillHandler | Wrapperが両方生成 | ファクトリパターン |

**循環依存の解決優先順位**（将来のESM化時に適用）:
1. 定義の分離（共通型/インターフェースの切り出し）
2. 依存方向の修正
3. 引数注入
4. 遅延getter
5. 動的importはコード分割目的のみ（循環回避には原則使用しない）

Phase 1では循環依存の**特定と記録**を行い、**解消はPhase 2bまたは将来のESM化時**に行う。

### 2.6 HTMLエントリポイントの整理

Deploy.batのHTMLコピー対象は7ページ（HeroStatusClusterer.htmlが含まれていない）。各エントリポイントが本番対象かローカル専用かを明確にする:

| HTMLファイル | Deploy.bat対象 | 本番/ローカル |
|-------------|---------------|-------------|
| AetherRaidSimulator.html | Yes | 本番 |
| ArenaSimulator.html | Yes | 本番 |
| SummonerDuelsSimulator.html | Yes | 本番 |
| DamageCalculator.html | Yes | 本番 |
| UnitBuilder.html | Yes | 本番 |
| StatusCalculator.html | Yes | 本番 |
| HeroIconLister.html | Yes | 本番 |
| HeroStatusClusterer.html | No | 要確認 |

### 2.7 成果物

- `dependency-graph.md` — ファイル間依存グラフ（テキスト形式）
- 各ファイルの副作用分類表
- 循環依存一覧と対処方針
- 依存レイヤー分類（Phase 2の設計に使用）
- Strict Mode違反の修正完了
- HTMLエントリポイントの本番/ローカル分類

## 3. Phase 2a: ディレクトリ再構成（物理移動のみ）

### 3.1 目的

Phase 1の依存分析結果に基づき、機能ドメインごとのディレクトリ構造を設計し、ファイルを再配置する。**グローバルスコープの今だからこそファイル移動のコストが低い**（ESM化後はimportパスの書き換えが必要になる）。

**このフェーズではファイルの物理的な移動のみを行い、JSコードの内容は一切変更しない。** ただし、以下の周辺ファイルのパス更新は必須:
- `create_tests.sh`のSOURCE_FILE_NAMESパス
- HTMLファイルのスクリプトロードパス（loadScripts配列）
- `Deploy.bat`のファイル参照パス
- `Local.js`のSKILL_EFFECT_FILES/SKILL_IMPL_FILES定義

### 3.2 ディレクトリ設計の原則

1. **依存関係に基づく分類**: Phase 1の依存グラフから自然なグルーピングを導出
2. **循環依存を可視化しやすい構成**: ディレクトリ間の依存方向が把握しやすいよう設計する（ディレクトリ構成で循環そのものは解消されないが、問題を見つけやすくする）
3. **適切な粒度**: 1ディレクトリ1-10ファイル程度を目安
4. **将来のbarrelファイル**: 各ディレクトリが将来`index.js`で公開APIを定義できる構造

**具体的なディレクトリ構成はPhase 1の分析結果で決定する。**

### 3.3 ファイル移動の手順

**鉄則**: ファイル移動とロジック変更は同時にやらない。フォーマット変更も混ぜない。

1. ディレクトリ構造を作成
2. `git mv`でファイルを新しい場所に移動（Git rename検出を確実にするため）
3. `create_tests.sh`のパスを更新
4. HTMLファイルのスクリプトロードパスを更新
5. `Deploy.bat`のパスを更新
6. `Local.js`のパスを更新
7. テスト実行 + 手動ブラウザ確認（本番対象の7ページすべて）
8. コミット

依存の強い塊をまとめて1バッチで移動する（HTML側のロード順・Deploy.bat・create_tests.shの追従コストを考慮し、バッチサイズは依存関係に応じて柔軟に決定する）。

### 3.4 update_skillsブランチとのコンフリクト対策

- **SkillImpl系ファイル**のパス変更は最小限にする。可能であれば移動せず現在の位置に維持
- `Local.js`と各HTMLの配列順序もコンフリクトポイント。移動バッチの最後にSkillImpl系のパスをまとめて更新する
- Phase 2a（ファイル移動）は集中的に進めて早期完了し、コンフリクト期間を短縮
- `git mv`を徹底し、Gitのrename検出を確実にする
- マージ手順をドキュメント化

### 3.5 成果物

- 新しいディレクトリ構成
- 更新されたcreate_tests.sh、HTMLファイル、Deploy.bat、Local.js

## 4. Phase 2b: 巨大ファイルの責務分割

### 4.1 目的

12,000行超のGod Objectを責務ごとに分割し、モジュール境界を明確にする。

**Phase 2aとは別のフェーズとして実施する。** ファイル移動（rename）とコードの構造変更を同時に行わないことで、git blame/bisectを維持し、回帰リスクを下げる。

### 4.2 BattleSimulatorBase.js（12,307行）— 最優先

現在6つ以上の責務が混在するGod Object。以下の責務を個別ファイルに分離:

- **コアフレーム**: コンストラクタ、初期化、ライフサイクル管理
- **バトルロジック**: ターン処理、戦闘シミュレーション
- **移動システム**: パスファインディング、移動可能範囲計算
- **コマンドキュー**: ユーザー操作のキューイングと実行
- **設定永続化**: セーブ/ロード、SettingManager連携
- **Vue統合レイヤー**: `#create_vue()`メソッドの切り出し — **分割の最後に回す**（Vue 2の`this`バインディングやリアクティブ参照が絡むため）

#### 分割の原則

- 切り出し先モジュールは**入力引数・返り値・外部状態依存・副作用対象**を明確にする
- BattleSimulatorBaseインスタンスを丸ごと渡す`function xxx(simulator)`パターンは避ける（God Objectの分散再生産になる）
- メソッド移動は1グループずつ、各ステップでテスト+ブラウザ確認
- git bisectが使えるよう細かくコミット

### 4.3 DamageCalculatorWrapper.js（17,193行）

- PerformanceProfile → 独立ユーティリティ
- 戦闘ユーティリティ関数 → 独立モジュール
- コアラッパーロジック → 維持

### 4.4 SkillEffect.js（9,632行）

- 基盤インフラ（ベースノード、Mixin定義） → 独立
- クエリノード群 → 独立
- エフェクトノード群 → 独立

### 4.5 SkillImpl系（SkillImpl202501.js: 21,875行等）

スキル実装ファイルは意図的に日付ベースで分割されており、この方式を維持する。ファイル自体の分割は行わない。

### 4.6 成果物

- 分割後のファイル一覧と各ファイルの責務定義
- 更新されたcreate_tests.sh（SOURCE_FILE_NAMES構成変更）
- 更新されたDeploy.bat（分割ファイルの追加/置換）
- 更新されたLocal.js（SKILL_EFFECT_FILES等の変更がある場合）
- 更新されたHTMLファイル（loadScripts配列の変更がある場合）

## 6. リスク管理

### 6.1 スキル実装ブランチとのコンフリクト

**リスク**: `update_skills`ブランチで継続されるスキル実装追加が、移行ブランチとコンフリクトする。特にPhase 2a（ファイル移動）で大量renameが発生し、Gitのrename検出限界を超える可能性。

**緩和策**:
- SkillImpl系ファイルはパス変更を最小限にする
- `git mv`を徹底し、フォーマット変更を混ぜない
- Phase 2aは集中的に進めて早期完了（コンフリクト期間の短縮）
- `Local.js`と各HTMLの配列順序変更もコンフリクトポイントとして認識
- マージ手順をドキュメント化

### 6.2 BattleSimulatorBase分割による回帰

**リスク**: God Objectの分割時に既存動作が壊れる。

**緩和策**:
- 分割前にBattleSimulatorBase関連のテストカバレッジを確認
- メソッド移動は1グループずつ、各ステップでテスト+ブラウザ確認
- Vue統合レイヤーの切り出しは最後に回す
- git bisectが使えるよう細かくコミット

### 6.3 依存分析の精度

**リスク**: 静的解析だけではグローバルJSの暗黙的な依存関係を完全には捕捉できない。`window["Foo"]`、動的プロパティ参照、Vueテンプレート内の参照等が見落とされる。

**緩和策**:
- 静的AST解析 + ESLint `no-undef` + 実行時グローバル差分の三段構えで補完
- 静的解析の不完全性を前提に、Phase 2aの移動時の実動作確認（テスト+ブラウザ）で不足分を補完する

## 7. 将来の展望: Vite/ESM移行

Phase 1-2b完了後、以下の課題を解決する具体計画を別途策定する:

- **ESM化の「足場」設計**: 各ページにmodule entryを作り、旧起動経路と新起動経路を併存させる方式
- **loadScripts()からの移行**: ページ単位でmodule entry化できる設計（一括切替ではなく段階的）
- **Deploy.batとの整合**: ESMコードは単純テキスト結合不可のため、Vite buildへの切替タイミングと方式
- **create_tests.shの廃止**: Vitest移行とテストのモジュール化
- **Strict Mode対応**: ESM化による自動Strict Mode適用への対処

本計画（Phase 1-2b）で整理されたコードベースは、これらの課題に取り組むための強固な基盤となる。
