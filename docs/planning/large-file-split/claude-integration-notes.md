# External Review Integration Notes

## レビュー元

- **Gemini** (gemini-3-pro-preview): スコープ/巻き上げの言語仕様リスクと運用面に焦点
- **OpenAI** (gpt-5.4): 依存関係の網羅性・HTML更新漏れ・テスト戦略に焦点

---

## 統合する指摘

### 1. `let`/`const` vs `var` スコープ問題 (Gemini A, OpenAI 2-3)

**指摘**: HTML loadScripts（個別`<script>`タグ）と結合テスト/Deploy.batでスコープが異なる。`let`/`const`はグローバルにならない。

**統合理由**: これはファイル分割時の根本的なリスク。見落とすとブラウザ実行時にReferenceErrorになる。

**統合方法**: 各Stepの事前チェックに「抽出対象コード内のトップレベル`let`/`const`を確認し、必要に応じて`var`への変更またはグローバル明示を行う」を追加。

### 2. ESLint `/* global */` コメント (Gemini C)

**指摘**: ファイル分割後、新ファイルで参照するシンボルが`no-undef`になる。

**統合理由**: 実務上確実に必要。CI通過に直結する。

**統合方法**: 各新規ファイルの先頭に `/* global ... */` コメントを追加する作業を各Stepに明記。

### 3. HTML更新対象の明示列挙 (Gemini C対象HTML, OpenAI 2-1)

**指摘**: 「該当するもののみ」では更新漏れが起きやすい。

**統合理由**: 具体性が上がり、チェック漏れを防げる。

**統合方法**: 実装前に `grep -l "DamageCalculatorWrapper\|Unit.js" Sources/*.html` 相当の調査を行い、対象HTMLを計画に列挙する旨を追記。

### 4. 3系統のロード順序一致チェック (OpenAI 2-2)

**指摘**: `create_tests.sh`、`Deploy.bat`、HTMLの間でロード順序が不一致になるリスク。

**統合理由**: 3箇所の順序を揃える確認は実装時の安全策として有効。

**統合方法**: 各Stepの検証項目に「3系統の相対順序が一致すること」を追加。

### 5. CombatResultTypeのロード位置の明確化 (Gemini A確認, OpenAI 4-3)

**指摘**: 「確認する必要がある」は曖昧。計画段階で特定すべき。

**統合理由**: 計画の具体性を上げる正当な指摘。

**統合方法**: 実装時に確認ではなく、計画段階でロード位置を調査し明記する。

### 6. 依存関係のより厳密な列挙 (OpenAI 1-1, 4-3)

**指摘**: 各抽出対象の外部参照を完全列挙するチェック項目を追加すべき。

**統合理由**: 「独立性が高い」の前提を実装前に検証するのは合理的。

**統合方法**: 各Step実装前に「非ローカル参照の完全列挙」を事前タスクとして追加。

### 7. 「ロジック変更禁止」ルール明記 (OpenAI 7-2)

**指摘**: typo修正・整形・ついで修正を禁止しないと差分レビューが困難。

**統合理由**: 移動のみのリファクタリングでは原則として正しい。

**統合方法**: 計画の制約セクションに「移動以外のコード変更を禁止」を追加。

### 8. smoke checkの具体化 (OpenAI 6-1)

**指摘**: 「HTMLが開く」だけでなく代表操作を定義すべき。

**統合理由**: ブラウザsmoke checkの基準が明確になる。

**統合方法**: 各Stepの検証項目に具体的な操作手順を追記。

### 9. UnitUtility抽出前の参照元確認必須化 (OpenAI 5-1)

**指摘**: Step B-2が最も危険。抽出対象関数の全参照元をgrepし、ロード順を確認すべき。

**統合理由**: グローバル関数の参照は広範囲に及ぶ可能性があり、事前の完全調査は妥当。

**統合方法**: Step B-2に事前タスク「全参照元grep + ロード順確認」を追加。

## 統合しない指摘

### PrecombatContextの移動先変更 (OpenAI 1-2)

**指摘**: BattleContext.jsではなくUnitContext.jsに入れるか、今回は見送るべき。

**不統合理由**: PrecombatContextは`copyTo`メソッドでBattleContextに値をコピーする設計であり、責務的にBattleContext側が適切。Geminiもこの判断を支持している。ただし、OpenAIの指摘する「全参照一覧の確認」は統合する（項目6に含む）。

### マージコンフリクト/コードフリーズ戦略 (Gemini B)

**指摘**: チーム内でのコンフリクト対策を追加すべき。

**不統合理由**: 本プロジェクトは実質個人開発であり、コードフリーズ・最優先マージの運用は不要。

### 単体テストの追加 (OpenAI 6-2)

**指摘**: PerformanceProfile、ScopedTileChanger等の単体テストを追加すべき。

**不統合理由**: 本計画のスコープは「移動のみ」であり、テスト追加は別の作業。既存テストで回帰検出は十分。

### ScopedTileChangerの例外安全性確認 (OpenAI 3-2)

**指摘**: dispose二重呼び出しやnull tileのケースを確認すべき。

**不統合理由**: 既存コードの品質改善であり、移動リファクタリングのスコープ外。動作は移動前後で変化しない。

### UnitUtil.withCacheのキャッシュ分析 (OpenAI 5-3)

**指摘**: キャッシュスコープやリークの確認が必要。

**不統合理由**: 挙動変更なし・移動のみであり、キャッシュ仕様の分析はスコープ外。

### Deploy.bat結合物での起動確認 (OpenAI 6-3)

**指摘**: 本番相当のDeploy.bat結合物でも起動確認すべき。

**不統合理由**: 開発環境がmacOSであり、Deploy.bat（Windows用）の実行は通常の開発フローに含まれない。HTMLでのブラウザ確認で代替する。

### privateメソッド記法の確認 (OpenAI 4-2)

**指摘**: `#method()`かconventionalか確認すべき。

**不統合理由**: 既存コードを移動するだけであり、記法は変わらない。ブラウザ互換性は既存の動作で担保済み。

### 行番号の陳腐化対策 (OpenAI 7-1)

**指摘**: 行番号はすぐずれるのでシグネチャも併記すべき。

**不統合理由**: 計画書にはクラス名・関数名が既に併記されている。行番号は参考情報として現状で十分。
