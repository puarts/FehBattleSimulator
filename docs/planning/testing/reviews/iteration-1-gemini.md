### 1. アーキテクチャと基盤に関する重大な問題

#### ❌ 1.1 `All.test.js` への統合による「スナップショット地獄」 (セクション 3.4 / 6.4)
`RegressionTestHelper` でスナップショットテスト（Jestの `toMatchSnapshot` など）を使用する場合、全テストが `All.test.js` 上で実行されるため、**すべてのテストのスナップショットが `All.test.js.snap` という単一の巨大ファイルに保存されます。**
*   **影響:** AIエージェントや複数の開発者が並行してスキルを実装した場合、この単一ファイルで**致命的なマージコンフリクトが頻発**します。
*   **解決策:** Jestの標準スナップショット機能に依存せず、JSONファイルとして `Tests/__snapshots__/[スキルID].json` のように明示的なファイルパスを指定して結果を保存・比較するカスタムアサーションを実装してください。

#### ❌ 1.2 カバレッジレポートの無意味化 (セクション 4.1)
結合された `All.test.js` で行カバレッジを測定しても、レポートには「`All.test.js` の 15,234行目が未カバー」と表示されるだけで、元のどのソースファイルのコードか特定できません。AIエージェントもこのレポートを修正に活用できません。
*   **解決策:** `create_tests.sh` でファイルを結合する際、**インラインソースマップ（Source Maps）を生成する処理を追加**してください。これにより、Jestのカバレッジレポートが元のファイル名と行数にマッピングされます。

#### ❌ 1.3 `create_tests.sh` の保守性低下とサイレントスキップ (セクション 2)
テストファイルを `case` 文でハードコードする方式は、新しいテストファイルを追加するたびにシェルスクリプトの修正を強制します。修正を忘れると、特定のカテゴリ実行時にテストが「サイレントにスキップ」され、擬似的な成功（False Positive）を生みます。
*   **解決策:** ハードコードをやめ、ディレクトリ構造による規約ベースのマッピングに変更してください。
    *   例: `Tests/skill/*.test.js`, `Tests/combat/*.test.js`
    *   シェルスクリプト側は `TEST_FILES=($(ls Tests/$1/*.test.js))` のように動的に取得する設計にします。

### 2. パフォーマンスとCIに関する懸念

#### ❌ 2.1 V8エンジンのJITコンパイルによるパフォーマンステストのFlakiness (セクション 5)
Node.js（V8エンジン）の特性上、初回実行時の処理時間はJITコンパイルのオーバーヘッドにより、2回目以降の数十倍の時間がかかります。単発で時間を計測してCIで閾値判定を行うと、極めて不安定（Flaky）なテストになります。
*   **解決策:** パフォーマンステストの前に必ず「ウォームアップ実行」を行ってください。
    ```javascript
    test('全英雄戦闘計算パフォーマンス', () => {
        // ウォームアップ（JIT最適化を促す）
        for(let i=0; i<5; i++) runCalculation();
        
        // 本計測
        const start = performance.now();
        runCalculation();
        const duration = performance.now() - start;
        expect(duration).toBeLessThan(1200);
    });
    ```
*   **代替案:** CIの共有ランナーの性能ブレは5倍でも収まらないことがあります。時間をハードな失敗条件（`expect`）にするのではなく、メトリクスとして出力し、閾値超過時はGitHub Actionsの `Warning` アノテーションをつけるにとどめるのが現実的です。

### 3. テスト設計とドメインロジック（FEH固有）の抜け漏れ

#### ⚠️ 3.1 ユニットのベースステータス変更によるリグレッション (セクション 6.3)
テストテンプレートで `UnitBuilder.fromHero('英雄名')` を使用していますが、将来のアップデート（神竜の花の上限解放、神装英雄の実装など）で既存英雄のベースステータスが変更されると、**スキル自体のロジックは正しいのに、結果の数値が変わってテストが落ちます。**
*   **解決策:** スキルのロジックテストには実在の英雄を使わず、すべてのステータスが固定（例: 全ステータス50）の `TestDummy` ユニットを生成するメソッド (`UnitBuilder.createDummy()`) を標準にしてください。

#### ⚠️ 3.2 グローバル状態の汚染漏れ (セクション 3.3)
`g_appData = null` のリセットだけでは不十分です。FEHのシミュレータでは以下のような状態がテスト間で漏洩する可能性が高いです。
*   **状態付与（バフ/デバフ/パニック等）のキャッシュ**
*   **奥義カウントの現在値**
*   **乱数シード（もし確率的要素が実装されている場合）**
*   **解決策:** `resetGlobalTestState()` は、ディープクローンで初期状態の `g_appData` を復元するか、メモリ上のユニットインスタンスを毎テスト完全に破棄・再生成する設計を徹底してください。

#### ⚠️ 3.3 FEH特有のEdge Cases（セクション 7 への追加提案）
戦闘ロジックテストの対象として、FEHで最もバグが起きやすい以下の相互作用が計画から漏れています。追加を強く推奨します。
*   **「戦闘開始時のHP」と「戦闘中のHP変動」の区別:** 祈り発動後や、戦闘前ダメージ（AoE）を受けた後の、HP条件スキル（例: 猛攻、待ち伏せ、HP25%以上条件）の評価タイミング。
*   **虚勢（Phantom Stats）の適用範囲:** 速さの虚勢などが、「追撃判定」には影響するが「ダメージ計算（例: 速さの○%をダメージに加算）」には影響しない、という切り分けのテスト。
*   **相性激化と相性相殺:** 武器相性の倍率変動と、それを無効化・反転する処理の優先度。

### 4. セキュリティ・運用上の考慮点

#### ⚠️ 4.1 並行実行時のファイル競合
現在 `create_tests.sh` は常に `All.test.js` という固定ファイル名を出力します。もしCIやAIエージェントが複数のカテゴリを並列で実行しようとした場合、ファイルの書き込み競合（Race Condition）が発生します。
*   **解決策:** 出力ファイル名をカテゴリごとに分ける（例: `out_skill.test.js`, `out_combat.test.js`）か、一時ディレクトリ（`mktemp`）を使用するようにスクリプトを修正してください。

#### ⚠️ 4.2 AIエージェント（Claude Code等）へのプロンプト指示
AIエージェントにテスト駆動で実装させる場合、既存のテスト（特に `All.test.js` のような巨大ファイル）を読み込ませるとコンテキストウィンドウを無駄に消費します。
*   **解決策:** 計画書（またはリポジトリの `README.md`）に、「AIは `run_tests.sh [category]` を実行してエラー出力のみを読み取ること。結合されたファイルを直接読まないこと」というガイドラインを明記してください。
