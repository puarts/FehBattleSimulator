## 統合する提案

### 1. `Object.assign` → `definePrototypeMethods` ヘルパー（両レビュー共通）

**理由**: 両レビューが最重要として指摘。non-enumerable化 + 重複定義検知を一箇所で実現できる。コスト低、安全性向上大。

**統合内容**: コアファイルに `definePrototypeMethods` ヘルパーを追加。全分割ファイルでこのヘルパーを使用。

### 2. ロード順序の固定化 + ガードチェック（OpenAI #2）

**理由**: 「順序自由」は誤解を招く。各分割ファイル冒頭でクラス存在チェックを入れることで、ロード順序ミスを即座に検出。

**統合内容**: ロード順序を「固定」に変更。各分割ファイル冒頭にガード追加。

### 3. Phase 1 のプレフライトチェック強化（Gemini A/B, OpenAI #3/#6）

**理由**: ファイルスコープ変数、`#` プライベートフィールド、インスタンス生成タイミングの事前確認は低コストで重要なリスク軽減。

**統合内容**: Phase 1 に3つの監査項目を追加。

### 4. `__canDisableSkillsFrom` の配置矛盾の解消（OpenAI #13）

**理由**: 明確な計画内の矛盾。横断的に使われるためコアに残すべき。

**統合内容**: 3.3の横断ユーティリティ一覧に含め、4.3/5.4から除外。

### 5. ファイル1のサイズ問題（OpenAI #9）

**理由**: ~7,600行は目標の3,000-5,000行を大幅に超過。ユーザーのインタビュー回答ではAtk/Defペアで1ファイルだが、`__init__applySkillEffectForUnitFuncDict`（6,842行）が突出して大きい。

**統合内容**: ファイル1を2分割（Atk/Def/Special + Unit）に変更。ファイル数は5→6に増加するが、目標行数内に収まる。

### 6. テスト戦略の強化（OpenAI #7）

**理由**: 存在確認だけでは不十分。constructor smoke test、代表メソッド呼び出しテスト、prototype shape snapshot を追加。

**統合内容**: テスト戦略セクションを拡充。

### 7. Phase ごとの commit 粒度（OpenAI #8）

**理由**: 1 phase = 1 commit は合理的。ロールバックが容易になる。

**統合内容**: 実装手順に commit 粒度を明記。

### 8. 循環依存の定義の明確化（OpenAI #5）

**理由**: 「循環依存なし」が何を指すか曖昧。実行時の相互呼び出しはあるが、トップレベル評価時依存がないことを明確化。

**統合内容**: 依存分析セクションの表現を修正。

### 9. ブラウザ検証の具体化（OpenAI #15）

**理由**: 「基本操作」だけでは不十分。consoleエラー確認、戦闘シナリオテストを明記。

**統合内容**: 最終検証セクションを具体化。

## 統合しない提案

### Gemini A: ファイルスコープ変数のリスク → 統合するが対応は異なる

Gemini は共有定数ファイルの抽出を提案したが、このコードベースではグローバルスコープでファイルが連結されるため、ファイルスコープ変数は実質グローバル変数。分割ファイルからもアクセス可能。ただしプレフライトチェックとして監査は行う。

### Gemini D: git blame の保存（コピー→削除戦略）

このプロジェクトは `create_tests.sh` でファイルを連結するテスト方式を使っており、git blame は主要な開発ワークフローではない。コピー→削除戦略は追加の複雑さに見合わない。通常の移動 + 明確な commit メッセージで十分。

### Gemini E: ESLint / IDE IntelliSense の問題

このコードベースはグローバルスコープ連結で動作しており、ESLintの設定もそれに合わせてある。prototype拡張でのESLintエラーは `browser` 環境設定で回避できるはず。IDE サポートは二次的な懸念。

### OpenAI #12: AST ベースのメソッド境界検出

一回限りのリファクタリングに AST ツーリングを導入するのは過剰。手動確認で十分対応可能。

### OpenAI #16: パフォーマンス初回ロード測定

Deploy.bat が最終的にファイルを結合・ミニファイするため、script ファイル数増加は本番に影響しない。

### OpenAI #17: prototype 汚染耐性

`definePrototypeMethods` の重複検知で十分カバー。追加のセキュリティ対策は不要。

### OpenAI #10: private 風命名の保守ガード

分割ファイル冒頭のメソッド一覧コメントは有用だが、計画レベルではなく実装時の判断。

### Gemini B: 辞書 init と lookup の同一ファイル化

ユーザーのインタビューで init メソッドの分離を明確に要望。init と apply は異なるタイミング・頻度で編集されるため、分離が妥当。
